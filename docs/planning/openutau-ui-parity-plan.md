# OpenUtau Web UI parity plan — Worker-first priority revision (draft)

**Status:** **Awaiting User Approval** — planning/source inspection only. No implementation, Session contract changes, Taskboard updates, branch/worktree creation, experiments, builds, or tests are authorized.

## Why this revision

This revision preserves the earlier source-based UI inventory and the finding that the basic Arrangement → Piano Roll editing handoff already works. The priority has changed: first harden the Direct WASM worker boundary, async Session transport, and render-job lifecycle (P0A–P0C); then advance Piano Roll editing (P1), incremental streaming (P2), Arrangement gestures (P3), and auxiliary UI (P4). The existing T020 worker implementation is credited, not treated as an unstarted gap.

The ownership boundary is unchanged: Rust owns project/musical data, mutations, undo/history, persistence, and render planning. React, Dockview, PixiJS, and Web Audio own layout, display, interaction, ephemeral gesture previews, and output-device playback. Do not add frontend-owned project state. A render-only worker may consume a Rust-authored immutable snapshot but must not become a second authority.

Evidence labels used below:
- **Source-verified:** confirmed by current repository source or contract text; static inspection only in this revision.
- **Previously runtime-verified:** a prior task record describes a browser/runtime check; not rerun for this planning revision.
- **Inferred:** follows from current code structure but needs an acceptance check.
- **Unverified:** no reliable source/runtime evidence yet; keep as an open decision or test.

## Priority order

**Overview:** P0A Direct WASM Worker isolation → P0B async Session transport → P0C render-job lifecycle → P1 Piano Roll editing (P1A–D) → P2 session-backed incremental streaming (P2A–C) → P3 Arrangement gestures/track tools → P4 project menus/auxiliary screens. Arrangement → Piano Roll remains a cross-cutting P0/P1 regression gate, not the P0 foundation itself.

### P0 — Worker-first Direct WASM foundation

**Goal:** keep the browser UI responsive while preserving one Rust authority for session/project state. The source already has a Direct WASM Session Worker; P0 hardens that path and closes its lifecycle/transport gaps rather than rebuilding it. P0 worker messages are an internal host protocol. They do **not** change frozen Project Session CONTRACT-v1; any public Session capability or contract change is a separate proposal and approval gate.

#### P0A — Direct WASM Worker isolation

**Current evidence**
- **Source-verified:** [`DirectWasmBackend`](../../ui-mock/react-dock/src/session-backends.js#L1-L20) constructs a module Dedicated Worker and boots it; [`wasm-session.worker.js`](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L25-L48) owns `WasmSessionRuntime`, which wraps the Rust-backed [`SessionDriver`](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L36-L45). The main-thread copy of `state` is a disposable snapshot; it is not the project authority.
- **Previously runtime-verified:** [T020](../work/tasks/T020-arrangement-worker-isolation.md#L19-L32) completed Direct WASM session/render isolation, PCM analysis, AudioWorklet playback, and synchronized playhead views; it reports a responsive UI during a long render. Credit this work. It did not claim that Rust Session mutations remain serviceable during the synchronous render call.
- **Source-verified:** OPFS and voicebank `fetch` adapters are used by the host (`ProjectStore` [`project-store.js`](../../web/app/project-store.js#L26-L46), [`samples.js`](../../web/samples.js#L166-L216)); WASM bindings use `wasm-bindgen`/`js-sys` in [`engine-wasm/Cargo.toml`](../../native/crates/engine-wasm/Cargo.toml#L10-L35). Worker-safe initialization must include WASM asset loading, OPFS availability, voicebank/media access, and failures; no DOM or canvas ownership moves into the engine worker. React/Dockview/PixiJS and the WebAudio/AudioWorklet output remain UI/host concerns.
- **Source-verified gap:** the backend rejects pending calls on `error` and terminates on close, but has no restart/recovery path or `messageerror` handler; boot errors terminate the newly created worker ([`session-backends.js`](../../ui-mock/react-dock/src/session-backends.js#L13-L20), [`#L54-L57`](../../ui-mock/react-dock/src/session-backends.js#L84-L86)). Failure must not silently switch a live project into a disconnected mock.

**Acceptance proposal**
1. Exercise worker boot, project create/open/save, edit/history, close, boot failure, worker error, malformed/`messageerror`, and renderer/session failure boundaries.
2. Prove React/Dockview/PixiJS remain responsive during an established long render, preserving T020’s existing acceptance; separately test a concurrent edit so UI responsiveness is not mislabeled Session responsiveness.
3. On initialization or worker failure, show an explicit error/preview state, reject all pending calls, and never present stale mock state as an editable live Rust session.
4. Define graceful close and crash recovery before implementation: renderer failure may be recoverable without losing the Session; Session-worker failure can restore only a known durable snapshot unless an approved Rust-owned recovery journal exists. Warn about unsaved state rather than promising to recover it.

#### P0B — Async Session transport, ordering, and backpressure

**Current evidence:** direct RPC is Promise-based and correlated by a numeric `id`, but the envelope is `{id, method, args}` without a discriminated/versioned message schema or Session/revision guards ([`session-backends.js`](../../ui-mock/react-dock/src/session-backends.js#L30-L56)); the Worker dispatches methods and serializes errors ([`wasm-session.worker.js`](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L21-L35), [`#L66-L95`]). The editor serializes high-level gesture mutations in [`engine.js`](../../ui-mock/react-dock/src/openutau/engine.js#L401-L411), but this is not a transport-wide bounded queue. The Direct WASM/HTTP factory and adapters exist ([`session-backends.js`](../../ui-mock/react-dock/src/session-backends.js#L90-L115), [`#L202-L205`]); their method/capability surfaces are partial rather than a complete uniform contract. This is host transport work, not permission to change the frozen Session contract.

**Design/acceptance proposal**
- Define a private, typed/discriminated host protocol (with a protocol version independent of CONTRACT-v1), request IDs, operation names/payload schemas, `sessionId`, expected/current `revision` where relevant, and explicit reply/error/change/job event types. Preserve the same async frontend interface across Direct WASM and HTTP; expose unsupported host operations as explicit capability errors, not accidental shape drift.
- Use a single ordered mutation lane per Session. Reads may be coalesced/cancelled only where safe; renders and lifecycle operations must have explicit admission/order rules. Bound pending request count, queued render jobs, asset bytes, and in-flight PCM bytes; return a backpressure/queue-full result instead of allowing unbounded memory growth.
- Ignore stale replies/events unless their request/job ID, Session identity, revision, and generation match the current consumer. A change event or render for an earlier revision must not replace a newer snapshot or publish into current playback.
- Transfer large `ArrayBuffer`s where ownership can move; use bounded asset batches and acknowledgements/backpressure. Avoid structured-cloning full voicebanks or PCM through the UI. Current `registerMedia` sends bytes through `postMessage` without a transfer list ([`session-backends.js`](../../ui-mock/react-dock/src/session-backends.js#L78-L80)); current playback copies the retained channels in the Worker before transferring them ([`wasm-session.worker.js`](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L51-L56)). Preserve the UI-owned AudioContext/AudioWorklet.
- Serialize structured errors with stable code/message and retryability where known; reject all pending calls on `error`, `messageerror`, timeout, protocol mismatch, or termination. Do not retry mutations automatically unless idempotency/revision rules make that safe.

#### P0C — Render-job lifecycle and Session/Render worker split

**Source-verified current behavior:** Direct WASM `renderMixdown()` awaits voicebank preparation and then calls synchronous `SessionDriver.renderMixdown()`/Rust `session_render_mixdown()` in the **same** Session Worker ([`wasm-session-runtime.js`](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L74-L84), [`session-driver.js`](../../web/app/session-driver.js#L194-L204)). During asynchronous bank preparation, the Worker may process other messages; during the synchronous WASM mixdown call it cannot dispatch Session mutations or cancellation until the call returns. Thus the **main UI remains responsive, but Session mutations are not responsive during active synchronous mixdown on this single Worker**. T020 verified UI responsiveness, not concurrent mutation service. The current Direct WASM path has no render `jobId`, progress, or cancel operation; the UI effect’s cancellation only drops the stale result ([`clone-state.jsx`](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L914-L958)).

**Recommendation for review:** retain the existing Session Worker as the sole owner of mutable Rust Session state. For P0C, target one bounded, separate **render-only Worker** for an immutable, Rust-authored snapshot so a synchronous render cannot block Session mutations; initially use one render worker, not a pool, until memory/throughput measurements justify concurrency. The render worker may compute from a revision-bound snapshot but must not own history, persistence, or mutable project authority. Reuse/adapt T011’s worker/job mechanics only where valid: its [`web/worker.js`](../../web/worker.js#L1-L23) and [`#L119-L178`] render planned track chunks with progress/cancel checks between yielded chunks, but `render_chunk()` itself is synchronous and this is not the current Session full-project mixdown product path ([T011](../work/tasks/T011-render-pool-product-wiring.md#L11-L20)). Whether the existing Rust snapshot/render surface can support a complete multi-track/media/FX render worker is an explicit P0C feasibility gate, not an assumption. If the split is not feasible, the single-worker fallback must say mutations wait until render completion and must not claim concurrent editing.

**Render job contract (internal worker transport only)**
- Capture one immutable Rust-owned render snapshot and `sessionId`/`revision` before asynchronous asset preparation. Revalidate that pairing before execution/publication. Current `prepareRenderBank()` reads project tracks before `await` calls and exports USTX later ([`wasm-session-runtime.js`](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L85-L151)); mixing data from different revisions is a risk to close, not a confirmed bug.
- Give every job `{renderId, sessionId, revision, generation}` and explicit states `queued → snapshot/asset preparation → running → done | soft-cancelled | cooperatively cancelled | failed | hard-terminated`. Report meaningful phases/timings; do not invent percent progress for a monolithic synchronous render. Publish results only if the job identity and snapshot revision still match the active consumer.
- **Soft cancel:** caller stops waiting/publishing and stale results are discarded; CPU work may continue. **Cooperative cancel:** render code checks a cancellation token at a documented yield/chunk boundary; the existing pool checks between chunks only, not inside one synchronous chunk. The current full Session mixdown has no cooperative stop point. **Hard cancel:** terminate the render Worker; it stops that job but loses its temporary runtime and must be recreated. Terminating a combined Session+render Worker would also lose the live Session, which is why the split is preferred.
- Define queue bounds, maximum active jobs, PCM/bank byte budgets, asset ownership, and cleanup of completed/failed/cancelled takes. A 288.4-second 44.1-kHz stereo float32 take is about 97 MiB for one buffer; [`stereoRender()`](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L10-L33) allocates channel/analysis buffers, and playback copies channels before transfer ([`wasm-session.worker.js`](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L51-L56)). Measure peak memory before enabling multiple full-project render workers.
- On render-worker failure, reject only its job, discard the stale result, replace the render worker, and leave Session state intact. On Session-worker failure, reject all calls and restore only the last durable Session state (or an explicitly approved recovery journal); never imply that unsaved in-memory mutations survived.

**Acceptance proposal:** render from a committed revision; edit the Session while a render is active and prove the edit applies promptly under the split design; reject a stale render after a newer revision; show progress phases without fabricated percentage; test soft/cooperative/hard cancellation separately; simulate both worker failures; verify job/asset/PCM queue limits, memory cleanup, and playback/export. Keep P0 job lifecycle separate from P2 incremental audio streaming: a completed-take render job is not early PCM delivery.

#### P0/P1 cross-cutting regression gate — Arrangement → Piano Roll

Protect the existing handoff; do not reimplement it. **Source-verified:** clicking a part dispatches `part/select` in [Arrangement](../../ui-mock/react-dock/src/openutau/arrangement-panel.jsx#L175-L183); the reducer updates `activePartId` in [clone-state](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L233-L243), and active part/notes flow into [Piano Roll](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L539-L555) and [its canvas](../../ui-mock/react-dock/src/openutau/piano-roll-panel.jsx#L858). **Previously runtime-verified:** [T004](../work/tasks/T004-web-editor-product-flow.md#L1001-L1018) records a scrolled Arrangement part click changing the Roll from 0 to 4 notes. The shared `CloneProvider` above Dockview suggests close/reopen should retain a valid active part, but that lifecycle check remains inferred ([main.jsx](../../ui-mock/react-dock/src/openutau/main.jsx#L228-L248)).

**Acceptance across the P0/P1 boundary:** (1) selecting a voice part updates Roll active part/notes; (2) closing/reopening the Roll dock retains still-valid selection; (3) Session snapshot refresh retains a valid part and safely clears a removed ID ([clone-state.jsx](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L235-L243)); (4) verify Direct WASM and HTTP where supported, including during/after Worker refresh and a render-job completion. “Refresh” means an in-session Session snapshot; hard-browser-reload persistence remains unverified. Double-click-to-open/focus and other Arrangement gestures stay P3.

#### P2A — Incremental playback MVP

Build the smallest correct path where:
1. Rust/Project Session produces finalized PCM chunks tied to a committed project revision.
2. Chunks follow the authoritative musical timeline; available audio can reach the AudioWorklet before the full-project render completes.
3. Rust remains authoritative for mixing, volume/pan, media parts, and track/master FX at their engine-defined points in the chain; preserve stateful DSP continuity across chunk boundaries.
4. Buffering, cancellation, basic pause/restart, and stale-revision protection are defined.
5. No second frontend mixer is introduced.

**Implementation entry:** do not start P2A until the feasibility gate is reviewed and the proposed frozen-contract/API extension is separately approved (or a source-backed, already-conformant path is demonstrated). **Acceptance:** first sound occurs before whole-project rendering completes; no duplicated/dropped frames at boundaries; measure and report underruns; test voice and wave parts; compare the resulting PCM against the existing sequential Rust render; verify Direct WASM and HTTP paths separately; perform playback checks only with a browser whose Web Audio clock advances. Require bit-identical PCM where the same deterministic mixer/render path permits it. If an implementation makes bit identity impossible, document and approve an explicit tolerance from a measured baseline before implementing it—no nonzero tolerance is approved or asserted in this plan. Verify that [T011's](../work/tasks/T011-render-pool-product-wiring.md#L72-L75) tail-mix guarantee is reused only within its tested scope, not generalized to arbitrary FX-bearing ranges.

#### P2B — Playhead-prioritized seeking

Add seek scheduling and chunk prioritization without losing FX history. Evaluate FX preroll, mixer/DSP state checkpoints, cache reuse, seek cancellation, buffer invalidation, and revision consistency. Do not assume arbitrary independent `mixFrom` ranges equal the sequential mix; P2A's tail-combine proof does not establish seek-state reconstruction.

#### P2C — Advanced streaming

Cover edit-during-playback, render scheduling/prioritization, long-project optimization, and cache/worker efficiency. Do not make P2B/P2C prerequisites for P2A unless a source-verified technical dependency requires it.

### Cross-cutting curve fidelity acceptance (P1B gate)

Treat **data fidelity**, **interpolation fidelity**, and **display fidelity** as separate dimensions. Create golden fixtures with identical projects and curve points for OpenUtau and Web; this plan defines the fixtures and checks, but does not run them.

| Dimension | Acceptance |
|---|---|
| Data fidelity | Stored points, simplification, undo/redo, persistence, and save/reopen agree; preview samples are not silently persisted as extra points. |
| Interpolation fidelity | Numerically compare curve values at fixed ticks/ms for identical point data, independently of the pixels. |
| Display fidelity | Compare authored path, transient gesture preview, and rendered/real path at matched zoom and viewport; check clipping/antialiasing and handle placement. |

**Pitch curves — source-verified mismatch to resolve:** React draws at about 3 px per segment; desktop samples about every 4 px. ## Risks, assumptions, and unresolved decisions

1. **P0C worker split feasibility:** the full multi-track Session snapshot, media/voicebank assets, and Rust mixdown must be reproducible in a render-only worker. T011’s chunk worker is not proof of that full-project path. If the split cannot preserve exact Rust render semantics, document the single-worker fallback and accept explicitly that Session mutations wait during synchronous mixdown.
2. **Mutation responsiveness and cancellation:** a synchronous Rust WASM call blocks its Worker’s message loop. Separate workers keep the Session responsive, but do not make the render computation itself cooperatively cancellable. Soft discard, between-chunk cooperative cancellation, and Worker termination must remain distinct; an intra-chunk stop needs a separate engine boundary.
3. **Snapshot consistency and stale replies:** current bank preparation crosses `await` boundaries after capturing project tracks, then exports the project later. Bind one Rust-owned immutable snapshot to a Session ID/revision before preparation; reject stale responses and never combine plan/assets/render data from different revisions.
4. **Worker failure and unsaved state:** a render-worker restart can preserve the Session only if Session authority is separate. A Session-worker crash may lose unsaved in-memory changes; recovery from the last durable save is not equivalent to recovering every mutation. Do not imply an autosave/recovery journal exists unless verified and approved.
5. **Memory/backpressure:** a long stereo float32 take, temporary channel/analysis arrays, a second transfer copy, cached audio, and sample-bank data can multiply heap use. Set queue/job/byte limits from measured workloads before considering more than one render worker.
6. **Arrangement → Roll regression:** current source retains a selected part only while its ID remains in the refreshed project. Confirm whether valid note selection must also survive dock close/reopen; hard-reload persistence remains unverified.
7. **Representative curves:** user review should identify one or two visibly wrong curves; the golden set still covers all five pitch shapes, sparse/dense curves, `sp`, and descriptor ranges. Do not diagnose smoothness solely from point count.
8. **[T014](../work/tasks/T014-project-session-openutau-controls-extension.md) boundary:** expression descriptor reads and the HTTP stroke-context route for a new curve are not solved ([T014](../work/tasks/T014-project-session-openutau-controls-extension.md#L217-L234)); frozen [CONTRACT-v1 §6](../CONTRACT-v1.md#L7-L12) remains unchanged. If the required public Session surface is absent, request separate contract review before implementation.
9. **Streaming host parity:** Direct WASM has a revision-bound RenderPool job harness but still advertises Session async jobs/cancel as unavailable and renders full-project mixdown synchronously; HTTP has immutable async jobs, progress, and per-job cancel but publishes audio only when complete. Neither host currently exposes incremental full-project PCM. P2A retains its adapter/API and separate contract gate; verify buffering, pause/restart, stale invalidation, and FX/media continuity before selecting a path.
10. **Stateful audio and media:** FX history must cross chunk boundaries. [T015](../work/tasks/T015-media-mixdown-and-real-project-render.md#L64-L84) established engine-owned wave/media mixing; [T018](../work/tasks/T018-openutau-flags-and-track-fx.md#L125-L147) records per-track FX/vibrato work, but its extension remains unratified. T015 also records ONNX-on-WASM as a known limitation; P0/P2 must not advertise unsupported renderers. [T017](../work/tasks/T017-audio-track-waveform-end-to-end.md#L604-L623) recorded a clock stuck at `00:28.000`; later [T020](../work/tasks/T020-arrangement-worker-isolation.md#L193-L200) verifies clocked playback of a completed mixdown, not streaming or concurrent edits. Do not infer acoustic speaker output from a render meter.
11. **No stale-gap resurrection:** [T019](../work/tasks/T019-openutau-web-ui-parity.md)'s completed track/mixdown wiring supersedes older structural gap notes; only carry forward gaps supported by current source/task evidence.
