# T032 — Full-project streaming feasibility (Wave 1)

## Executive finding

This source-only review finds a material difference between the existing T011 render-pool harness and true full-project streaming. T011 can make an early **per-track voice chunk** available; the current Session mixdown and browser playback paths still construct, copy, and hand over a completed full-project take before playback. Neither the Direct-WASM Session API nor the native HTTP render-job API currently provides ordered, bounded, progressively consumable full-project PCM.

A Rust-owned stream producer appears feasible as a separately designed Session/API change, but it is not a wiring-only task. The producer must render against one committed revision, plan and mix every voice and wave contributor in global time order, preserve track-FX state and tails, bound memory/backpressure, and publish blocks against the audio clock. Recommend **proceed to a separate API/host design review only; defer T033 implementation** until Session/API and audio-host review approve the contract and measured acceptance targets. Keep completed-take rendering as fallback. This report proposes no thresholds and does not change the frozen contract.

## Proposed API — NOT APPROVED

The approved APIs cannot supply bounded full-project PCM blocks with revision pinning, block ordering and an externally controlled stream lifetime. The following is a candidate Rust-owned Session surface for review only; names, ownership/borrowing, serialization and exact field schema all require approval. Do not treat it as contract text and do not update CONTRACT-v1 in T032.

    pub fn session_render_stream_begin(
        &mut self,
        expected_revision: u64,
        options: SessionRenderStreamOptions,
    ) -> Result<SessionRenderStreamInfo, String>;

    pub fn session_render_stream_next(
        &mut self,
        stream_id: &str,
        max_frames: u32,
    ) -> Result<SessionRenderBlock, String>;

    pub fn session_render_stream_cancel(
        &mut self,
        stream_id: &str,
    ) -> Result<(), String>;

    pub fn session_render_stream_close(
        &mut self,
        stream_id: &str,
    ) -> Result<(), String>;

Candidate stream info should identify stream/session/revision, sample rate, channel count, and any known duration/format. Each block should carry stream generation, revision, sequence, frame_start, frame_count, channels, sample_rate, PCM and explicit status (data, terminal, cancelled, stale/conflict, or error). Blocks must be bounded; empty/nonterminal and end-of-stream semantics must be unambiguous. API consumers must not have to infer timeline order from worker completion order.

The Direct-WASM adapter could expose begin/next/block/cancel/close worker messages with transferable bounded PCM; the native adapter could expose an equivalent render ID and bounded pull or block events plus cancellation. Existing HTTP completed WAV retrieval and async job polling are not themselves this streaming interface. The producer must be backed by Rust’s render/session semantics, not a JavaScript project-mixer that becomes a second source of truth.

## Measurement-based acceptance proposal (no thresholds set)

1. **Latency and throughput:** For named cold/warm project fixtures, record request-to-first-valid-block, request-to-audible-start, full producer completion, and p50/p95. Include silence at the timeline start so “first audio” is defined as the first scheduled block for the requested position, not merely the first nonzero sample. Demonstrate that first playback can begin before full completion on qualifying workloads. Record render throughput, block production time, queue depth and consumer rate.
2. **Underrun and clock:** Record every underflow’s count, duration, position and policy response under the actual audio clock. Compare AudioWorklet consumed frames and UI transport position through start, pause/resume, seek, end, and output/sample-rate variations. Define the acceptable rate only after target-device baselines and product targets are approved.
3. **PCM continuity/reference:** Concatenate blocks and compare against the existing whole-project offline Rust mixdown reference for complete projects containing multiple voice tracks, wave-only and mixed tracks, voice/wave overlaps, missing/silent media, chunk seams/context, FX boundaries/tails, seek points and project end. Report sample-wise mismatch count, max/RMS difference, gaps/duplicates and channel/rate behavior. Preserve exact equality where the arithmetic order makes it expected; otherwise establish and approve tolerance from repeatable reference measurements, not assumption.
4. **Freshness, cancellation and ordering:** Force out-of-order worker completion, edit during render, voicebank/media revision change, seek during playback, cancel during an active and queued job, and rapid start/stop. Verify sequence/frame monotonicity, stale-generation discard, no post-cancel blocks, no stale revision audible/published, resource cleanup, and offline-reference parity after a new generation.
5. **Memory/device/host:** Instrument WASM and JS heaps, media/sample buffers, transfer copies, queue occupancy, peak RSS where available, GC pauses and device audio behavior over actual target project/voicebank/media sizes. Sweep each supported browser/device and both Direct-WASM and HTTP adapters; include AudioWorklet-unavailable fallback. Report measured baselines and device failures. Product limits and pass/fail thresholds need explicit owner approval after these measurements.

## Recommendation and gates

**Proceed only with separate design/API review.** The existing per-track pool and static-take player are useful precedents for ordered worker results and clocked playback, but neither constitutes full-project streaming. A Rust producer must own revision snapshot, global voice+wave ordering, stateful track processing and bounded block lifetime; the client should own bounded delivery/backpressure and audio-clock consumption.

**Defer T033 implementation** until the API proposal, stream block/status semantics, stale-revision and cancellation behavior, AudioWorklet/fallback policy, and target host matrix are reviewed and approved. Then establish baselines with the acceptance plan above and set no thresholds until measured and approved. Until a stream sink exists, retain completed-take rendering as the reliable fallback, and clearly handle AudioWorklet absence instead of presenting a full mixdown path as incremental playback.
