# T024 Wave 1 — Render-snapshot feasibility

**Scope:** source-only feasibility review. No implementation, tests, builds, contract edits, or board/task edits were performed. This report is the only new artifact authorized for this pass.

## Decision

A separate, bounded Render Worker is **architecturally plausible**, but the current product path is **not ready to implement as a full immutable render job**. The current Rust/Web boundary captures a committed USTX and revision, while full mixdown also reads Session-side pronunciation state and live Engine-owned voicebank/sample/media stores. The project snapshot does not pin those assets to immutable bytes or generations. A second Worker would have its own Engine and WASM memory, and rendering has significant, presently unmeasured memory duplication. Do not start implementation until the T023 handoff, an explicit implementation approval, and a measured single-job memory budget exist. The existing T024 preliminary statement that track FX is incomplete is stale; the Rust full-project path already applies the implemented FX described below.

Evidence levels used here: **High** means directly visible in cited source/records; **Medium** means an architectural inference or calculation from recorded inputs; **Unknown** means the source records do not measure or establish it.

## What the current boundary actually captures

- **High — Session state is not a complete render snapshot.** The current browser adapter synchronously captures and freezes Rust-authoritative session ID, revision, and canonical USTX, then rejects results whose session ID/revision no longer match. It converts a Rust u64 revision to a JavaScript Number and rejects values outside the safe-integer range. The envelope does not carry pronunciation selections, bank/sample assets, wave-media bytes or generations, or render/build configuration. See [session-render-contract.js](../../web/app/session-render-contract.js#L24-L75).
- **High — Pronunciation selections are a separate Rust-owned input.** Session stores canonical USTX and revision, while committed pronunciation selections are resolved from stable-ID sidecar state. Full mixdown reads the live Session YAML, reads those per-track selections separately, and consults the Engine’s live voicebank, sample source, and media source. The current WASM method supplies a newly-created false cancellation flag and no progress callback. It returns the entire stereo vector, not a streamed full-project result. See [project-session/session.rs](../../native/crates/project-session/src/session.rs#L275-L347) and [engine-wasm/lib.rs](../../native/crates/engine-wasm/src/lib.rs#L303-L335).
- **High — Track FX is already part of the project render.** The mixdown builds a stereo bus per track, adds voice and wave parts, applies enabled track UMixFx, then sums the buses. T018 records EQ → stereo-linked compressor → Freeverb, fader/pan, and stereo handling. Therefore T024’s preliminary “FX incomplete” checkpoint should not be carried forward as a current blocker. See [pipeline.rs](../../native/tools/synth-cli/src/pipeline.rs#L962-L1021), [T018](../work/tasks/T018-openutau-flags-and-track-fx.md#L131-L166), and the stale note in [T024](../work/tasks/T024-render-worker-lifecycle.md#L40-L44).
- **Medium — A complete Rust-authored envelope needs an asset-manifest boundary.** It should atomically bind session ID, exact revision (not an unsafe JS-number conversion), canonical USTX including FX, pronunciation selections, render options/build identity, voicebank identity/configuration, and the required WAV/FRQ and wave-media references with immutable generation IDs or content digests. The files themselves may be transferred under explicit ownership or read by the Render Worker from immutable/versioned OPFS keys. A mutable bank root, path, media ref, or UI cache epoch alone does not pin bytes. Current sources do not expose this complete DTO or pinning mechanism.

## Assets, copies, and ownership

- **High — Each Worker would have independent Engine state.** The Engine owns its Voicebank, MemorySource, MemoryMediaSource, and Session. The browser runtime plans voice tracks and loads needed WAV/FRQ entries from OPFS into that Engine. A separate Worker cannot use the Session Worker’s Engine or linear memory in the current architecture; it must load its own Engine/assets or receive owned data. See [engine-wasm/lib.rs](../../native/crates/engine-wasm/src/lib.rs#L138-L145), [wasm-session-runtime.js](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L85-L152), and [samples.js](../../web/samples.js#L199-L223).
- **High — The currently loaded decoded sample cache is cloned again for mixdown.** session_render_mixdown constructs MemoryRenderer with self.source.clone(). MemorySource is a cloned HashMap of ResolvedSample; each entry owns WavData.samples as a vector of f32 and optional FRQ bytes as a vector. Its resolve method also returns cloned WAV/FRQ values. This is concrete extra copy pressure during a render, not just a theoretical second-Worker cost; actual bytes depend on the project’s loaded sample set and are not measured. See [engine-wasm/lib.rs](../../native/crates/engine-wasm/src/lib.rs#L314-L316), [source.rs](../../native/crates/worldline-rs/src/source.rs#L15-L22), [source.rs](../../native/crates/worldline-rs/src/source.rs#L49-L52), [wav.rs](../../native/crates/voicebank/src/wav.rs#L10-L18), and [source.rs](../../native/crates/worldline-rs/src/source.rs#L91-L99).
- **High — Wave media is copied into Rust-owned storage.** ProjectStore persists media in OPFS and returns a Uint8Array; the runtime registers it with Rust. session_register_media stores bytes.to_vec(). A new Engine must re-register/reload the wave media, or use an explicitly transferred buffer/immutable OPFS object. T017 confirms the browser relink flow persists imported wave bytes and registers a stable media ref. See [project-store.js](../../web/app/project-store.js#L180-L197), [engine-wasm/lib.rs](../../native/crates/engine-wasm/src/lib.rs#L190-L198), and [T017](../work/tasks/T017-audio-track-waveform-end-to-end.md#L461-L481).
- **High — The current bank key is not a content version.** The runtime uses opfs:<root> as its bank key and tracks loaded sample keys; it does not fingerprint file contents. The UI’s bankEpoch invalidates render/playback caches on voicebank install/uninstall and appears in UI cache keys, but it is not part of the current Rust render envelope and is not a byte-level asset pin. See [wasm-session-runtime.js](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L104-L150) and [clone-state.jsx](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L312-L312), [clone-state.jsx](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L441-L443), [clone-state.jsx](../../ui-mock/react-dock/src/openutau/clone-state.jsx#L927-L958). The runtime’s root-based cache and UI epoch serve different purposes; neither proves that a later OPFS read returns the bytes used when the snapshot was captured.
- **High — Transferables move ownership; they do not make the WASM output zero-copy.** Posting an ArrayBuffer with a transfer list detaches it from the sender and avoids structured-clone duplication if the sender gives up ownership. Existing chunk rendering explicitly calls slice() to copy out of WASM memory before transferring the new buffer. The mixdown worker retains its two channel arrays in a take cache; getPlaybackTake uses channel.slice() before transferring playback data, adding another transient copy. See [worker.js](../../web/worker.js#L149-L165) and [wasm-session.worker.js](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L51-L56), [wasm-session.worker.js](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L78-L92). Re-reading OPFS avoids transferring the source archive but still requires worker-local decoding and Engine storage.

## Responsiveness, job lifecycle, and cancellation

- **High — A second Worker could leave the Session Worker available, but the current single Worker cannot.** T020 proves that moving Direct-WASM work off the browser UI thread keeps the UI responsive. The current WASM Session Worker is one async RPC dispatcher; after the async asset-preparation awaits, renderMixdown calls synchronous WASM. While that call runs, the Worker event loop cannot receive an edit or cancellation message. T020 does not demonstrate Session edits being accepted during that synchronous call. An independent render-only Worker with its own Engine is the plausible way to preserve Session Worker responsiveness, subject to snapshot and memory constraints. See [T020](../work/tasks/T020-arrangement-worker-isolation.md#L19-L32), [wasm-session.worker.js](../../ui-mock/react-dock/src/openutau/wasm-session.worker.js#L25-L94), and [wasm-session-runtime.js](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L80-L84).
- **High — Current full mixdown does not expose cancellable progress.** The lower-level pipeline accepts a cancel AtomicBool and progress callback, checks cancellation at chunk entry, and reports the literal error “render cancelled”; it cannot interrupt a chunk already executing. The WASM API passes a local false flag and no callback for progress. Because the WASM call is synchronous, message-based soft cancel cannot be observed until it returns. Hard cancellation can terminate the isolated Render Worker; the owner must reject its pending job and recreate the Worker. Cooperative cancellation would require a deliberately supported shared signal or yielding/chunking with message opportunities, plus explicit progress wiring. See [pipeline.rs](../../native/tools/synth-cli/src/pipeline.rs#L947-L959), [pipeline.rs](../../native/tools/synth-cli/src/pipeline.rs#L1218-L1229), and [engine-wasm/lib.rs](../../native/crates/engine-wasm/src/lib.rs#L317-L335).
- **High — T011 mechanics are useful but not proof for whole-project mixdown.** T011 has revision-bound job IDs, FIFO chunk scheduling, per-chunk progress/cancel, stale-result checks, and worker recovery; the chunk Worker yields between chunks so it can observe cancel messages. That is a single-track/chunk harness. It does not turn the synchronous full-project session mixdown into a message-interruptible job. Reuse the lifecycle pattern, not its memory assumptions or a multi-worker pool. See [T011](../work/tasks/T011-render-pool-product-wiring.md#L13-L19), [worker.js](../../web/worker.js#L139-L178), and [pool.js](../../web/pool.js#L292-L368).
- **Medium — Minimum safe lifecycle for an approved implementation:** use one active render job initially; bound or reject excess queue submissions; tag every accepted/running/progress/terminal/error/result event with job ID, session ID, exact revision, and asset generation. Report phases/units explicitly (asset preparation, render chunks/tracks, terminal status). Before publication, verify that the job is still active, not cancelled, and still matches the current session revision and asset generation. Never publish stale, failed, cancelled, or partial mixdown audio. On Worker error/termination, fail active and queued requests deterministically, discard the worker-owned result, and replace the Worker. These are recommendations, not existing guarantees.
- **High — Same-Worker fallback blocks edits.** If a separate Render Worker is not approved or cannot fit the memory budget, synchronous mixdown must stay on the Session Worker; edits and other Session RPCs then wait until it returns. The browser UI can remain responsive, but the Session itself is not available for edits during the render. This is the fallback already recorded in T024.

## Memory floor (derived, not a peak measurement)

T015 records a 288.4-second, 44.1-kHz real-project mixdown, with four voice tracks, 153 phrases, one wave part, and a 474.5-MB voicebank archive; it also notes approximately 10 seconds to decode the 288-second MP3 per mixdown. The archive size is not the decoded in-memory sample set. No cited record measures peak browser/WASM memory. See [T015](../work/tasks/T015-media-mixdown-and-real-project-render.md#L88-L95) and [T015 decode note](../work/tasks/T015-media-mixdown-and-real-project-render.md#L173-L175).

For that recorded duration, 288.4 × 44,100 = 12,718,440 frames:

| Buffer inventory | Bytes | Approx. MiB | Evidence |
|---|---:|---:|---|
| Interleaved stereo f32 result (2 values/frame) | 101,747,520 | 97.0 | Derived from duration/rate; whole-project Rust result is a vector of f32. |
| JS left, right, and mono analysis Float32Arrays (3 values/frame) | 152,621,280 | 145.6 | Derived from stereoRender allocations. |
| Interleaved + those three arrays during conversion | 254,368,800 | 242.6 | Lower-bound array inventory, before render assets and work buffers. |
| Possible additional live Rust output during WASM-to-JS copy | ~101,747,520 | ~97.0 | Conditional overlap; must measure rather than assume. |
| Playback channel.slice() copies while cached channels remain | ~101,747,520 | ~97.0 | Transient transfer copy for both channels. |

The JS split happens after the full Rust mixdown has been built. The pipeline also holds track/final buses and phrase temporaries; the Engine has loaded samples; mixdown clones the decoded sample cache; wave media must be decoded; and a separate Worker would hold its own Engine/memory/assets. These cannot be reduced to one reliable peak number from source inspection. The figures above are a floor/inventory, not a peak estimate or a go/no-go budget. stereoRender allocation evidence: [wasm-session-runtime.js](../../ui-mock/react-dock/src/openutau/wasm-session-runtime.js#L10-L34).

## Required handoff before implementation

1. **Wait for T023/T022 sequencing and explicit approval.** The board says T023 and T024 implementation are blocked; T023 also requires a single owner for shared Worker/protocol files and explicit queue/payload/ownership decisions. Do not edit the shared Worker, RenderPool, Session API, or frozen CONTRACT-v1 during this feasibility pass. See [BOARD.md](../work/BOARD.md#L34-L36), [BOARD.md ownership note](../work/BOARD.md#L82-L82), [T023](../work/tasks/T023-wasm-session-transport.md#L18-L41), and [T024](../work/tasks/T024-render-worker-lifecycle.md#L17-L21).
2. **Ratify the snapshot/asset boundary first.** Define exact revision representation, pronunciation sidecar inclusion, render/FX/build identity, voicebank and media asset generations/digests, and whether the Render Worker reads immutable OPFS generations or receives transferred owned buffers. A host root/path or current {sessionId, revision, ustx} is insufficient.
3. **Measure before choosing the worker count.** Measure a cold and warm render of the real voice+wave project: loaded decoded sample bytes/count, MP3 decoded bytes, render-time MemorySource clone cost, WASM linear-memory peak, JS PCM peak, transfer peak, latency, and cleanup after success/cancel/failure. Start with one render Worker and no pool expansion; set measured queue and payload limits.
4. **Verify parity and lifecycle only after approval.** Check output parity against current Rust render, FX/wave inclusion, edit acceptance during rendering, stale revision and asset-generation rejection, hard/soft cancel behavior, Worker failure/restart, and memory cleanup. The T011 single-track harness is not a substitute for this full-project evidence.

**Bottom line:** separate rendering is a credible direction, not an implementation-ready capability. Current full-project mixing is synchronous, live-state-bound, uninterruptible by Worker messages, and memory-heavy; the immutable asset manifest, T023 transport semantics, and peak-memory budget remain unresolved.
